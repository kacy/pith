# internationalization

`std.text` makes text correct for everyone. `std.intl` makes it *different* for
different people: which language to answer in, which form of a message a count
takes, and what to do when the locale someone asked for is not one you have.

The dependency runs one way. `std.text` never imports `std.intl`, so a program
that only needs correct text does not pull in locale data. `std.intl` imports
`std.text`, because choosing what to say is no excuse for getting the
characters wrong.

## the model

This follows gettext and Rust's `fluent` rather than ICU.

Messages live in a catalog keyed by locale. A lookup walks a fallback chain
until something answers. Plural forms are separate catalog entries selected by
CLDR category.

ICU takes the other route: one message string carries its own embedded
`select`/`plural` grammar. That is more expressive, and it also means every
translator has to learn a small programming language, and every such string is
a place a translator can introduce a syntax error you only find in production.
Keeping the plural choice in the catalog's *structure* keeps the strings
translatable by people who translate. The cost is that a message needing two
independent plurals has to be split, which is rare enough to be worth it.

## locales

```pith
import std.intl as intl

locale := intl.parse_locale("pt_BR")   # language "pt", region "BR"
intl.locale_tag(locale)                # "pt-BR"
```

Tags are canonicalised by shape, as BCP-47 recommends: language lowercase,
script title case, region uppercase. `EN-us` and `en-US` parse to the same
locale, which is what makes a tag from a browser, a config file and a database
comparable at all.

Lookup drops subtags from the right:

```pith
intl.fallback_chain(intl.parse_locale("zh-Hant-TW"))
# ["zh-Hant-TW", "zh-Hant", "zh-TW", "zh"]
```

For a server, the entry point is usually the `Accept-Language` header:

```pith
wanted := intl.parse_accept_language(request.header("Accept-Language"))
chosen := intl.best_match(wanted, ["en", "de", "pt-BR"]).unwrap_or("en")
```

`parse_accept_language` orders by quality value and treats `q=0` as a refusal
rather than a weak preference, which is what the header actually means.

## plurals

This is the part programs get wrong without a table.

English has two forms, so code grows an `if count == 1` and every other
language is wrong. Polish needs four forms and picks between them on the last
two digits. Arabic uses all six CLDR categories. Japanese has one form for
everything, so an English-shaped message reads as broken even when the
translation is perfect.

```pith
intl.plural_category("en", 1)    # "one"
intl.plural_category("en", 0)    # "other"
intl.plural_category("pl", 2)    # "few"
intl.plural_category("pl", 5)    # "many"
intl.plural_category("pl", 22)   # "few"
intl.plural_category("ja", 42)   # "other"
intl.plural_category("ar", 0)    # "zero"
```

Note `pl` at 22 and 5: no rule of thumb gets that right, which is the point of
having the data.

A few languages differ by region, and CLDR says so — European Portuguese
counts `0` as `other` where Brazilian counts it as `one` — so the lookup walks
the fallback chain rather than jumping straight to the language subtag.

**Integers only.** CLDR rules can distinguish `1` from `1.0` through operands
that describe the visible fraction digits. An `Int` has none, so those operands
evaluate as zero here. Counting things is the case this serves; formatting
`1.0` items is not.

## catalogs

```pith
messages := intl.catalog("en")
intl.add(messages, "en", "greeting", "Hello, {name}")
intl.add(messages, "de", "greeting", "Hallo, {name}")

intl.add_plural(messages, "en", "files", "one", "{count} file")
intl.add_plural(messages, "en", "files", "other", "{count} files")
intl.add_plural(messages, "pl", "files", "one", "{count} plik")
intl.add_plural(messages, "pl", "files", "few", "{count} pliki")
intl.add_plural(messages, "pl", "files", "many", "{count} plików")

intl.plural(messages, "pl", "files", 22, {})   # "22 pliki"
```

`count` is always available as a placeholder, so a message does not have to be
passed its own count twice.

Two deliberate choices about failure. A missing key renders as the key itself
rather than an empty string, so a gap in a translation is visible in the
output instead of silently disappearing. An unknown placeholder is left
exactly as written, so a translator who mistypes a name sees it rather than
losing the value.

A half-translated plural falls back to the language's `other` form before it
gives up, which is what a catalog looks like partway through translation.

> Writing `{name}` in pith **source** needs `{{name}}`, because a single brace
> starts a string interpolation. Messages loaded from a file at runtime are
> unaffected.

## the tables

Plural rules come from CLDR, pinned at **48.2.1**:

```
python3 tools/intlgen/generate.py
```

This is a separate generator from `tools/unicodegen` because it draws on a
different body of data with its own release cycle. Unicode says what a
character is; CLDR says what a language does with it.

CLDR covers 224 locales with only 40 distinct rule sets between them — English,
German and Swedish all count the same way — so the table maps locales onto a
much smaller list of rules, and comes to 4 KB.

Rules keep the shape of the CLDR source so the generated file can be read
against it:

```
cldr:  v = 0 and i % 10 = 2..4 and i % 100 != 12..14
here:  v=0&i%10=2..4&i%100!12..14
```

The generator checks its output against the sample values CLDR publishes
alongside every rule — the `@integer 0, 2~16, 100` lists — which are the
standard's own statement of which numbers fall in which category.

## what is not here

Locale-aware number and date formatting, ordinal plurals (`1st`, `2nd`),
currency, and collation.

Those need CLDR's per-locale data, which is hundreds of files rather than the
one this module's tables come from. Adding them is a data-pipeline job rather
than an API design one, and shipping a guessed-at separator table would be
worse than shipping nothing. `plural_category` is here because it is the piece
programs get wrong *without* a table, and cannot get right by trying harder.
